## Required transaction sequencing

1. Validate before mutation. Host-attested signature/type/fee/blob checks must be explicitly bounded, never silently treated as implemented recovery or consensus validation. Check sender nonce/code, affordability at maximum fee, intrinsic/floor and host capacity. Derive create address from sender preincrement nonce. Debit actual effective-price gas limit plus actual blob fee and increment sender nonce once. These changes survive valid included transaction failure.
2. Take preparation snapshot after sender debit/nonce. Apply authorizations sequentially. Warm recovered authorities before code/nonce checks; invalid tuple costs intrinsic but skips mutation. Charge absent leaf, first unpaid write, and first net-new designation separately. Sender and value-bearing recipient have paid writes; creation recipient also does (fork.py 605-608). Commit authorization state gas after successful authorizations: move spill to committed spill, set baseline to current reservoir, zero refundable spill.
3. Warm sender, recipient, coinbase, exact active precompiles, access list and recovered authorities. CREATE checks deployability before state charge. Deployability is zero nonce and empty code, ignoring balance/storage (state_tracker.py 348). Its state charge tests transaction pre-state EMPTY_ACCOUNT (interpreter.py create_evm), not a blindly reused opcode collision predicate. CALL charges new recipient state when nonzero value and not alive, then resolves delegation one hop and charges delegated target access. Delegating to a precompile executes empty code; second designation is ordinary invalid bytecode.
4. Preparation exception restores the preparation snapshot including authorization changes; restores entire entry reservoir and all committed/refundable spill, then burns all execution gas. Return no output/logs/deletions. Sender upfront debit and nonce remain. Execution snapshot instead preserves successful authorizations; dispatched REVERT/exception restores only execution changes and refundable state charges. REVERT returns remaining execution gas and output; exception burns gas and clears output. Reset execution refund on failure.
5. CREATE starts depth zero, executes initcode with empty calldata, resets destination storage and transaction-original slots, marks created, sets nonce one and retains preexisting balance. Transfer value/log belongs inside execution rollback. Successful deployment rejects leading ef and output above 65536, pays hash execution 6*ceil(n/32), state 1530*n. Deposit failure undoes destination changes and burns execution gas. No extra creator nonce increment beyond transaction increment.
6. For settled top meter G,R and signed net state S, pre-refund U=T-G-R; execution refund=min(U/5,max(F,0)); sender gas=max(U-refund,floor); unused=T-senderGas. Block state=max(S,0); block execution=max(U-blockState,floor), before execution refunds. Auth committed state usage must be included. State credits are already reflected in pools and must not also enter F. Preserve arbitrary Nat gas/reservoir or explicitly validated host bounds.
7. Credit payer unused*effectivePrice and coinbase senderGas*(effectivePrice-baseFee) before selfdestruct cleanup. Blob fee is not refunded. Fees do not emit ETH transfer logs. Then for successful deletion set clear nonce/code/storage but **preserve current balance** (fork.py 1061-1097; state_tracker.py 480). Refunded/replenished balances, including a coinbase fee to a destroyed account, can survive. Delete the leaf only if empty after clearing.

## Existing helper integration hazards

- `runtime.bend:run` unconditionally chooses precompile by `frame.address`. Top CREATE must suppress that even if its destination is a precompile address; delegated execution must use resolved dispatch semantics. An explicit prepared runner should bypass this automatic override.
- `vm.bend:finished` returns true on top-level terminal action. `call-finish.bend:unwind` with Nil parents is a no-op. Therefore Runtime.run alone neither settles top rollback nor deposits top CREATE code. Transaction finish must perform both exactly once.
- `create-enter.bend:collision` also rejects nonzero storage, contrary to pinned deployability. Do not reuse for transaction create. Existing nested helper also retains old original slots when clearing storage; transaction layer cannot honestly claim that fixes all nested create cases.
- Existing Engine tracks state_used and refundable state_spilled but no committed spill. Save auth charge totals externally and start fresh execution-local accounting after commit; otherwise refunds during execution can incorrectly repay committed auth execution spill.
- HostLimit is not an Ethereum exceptional halt. Preserve it as an explicit unsuccessful host outcome; do not publish its partial execution world or a consensus receipt.
- Reset per-transaction warmth, storage warmth, transient, logs, refunds, created/deletion markers and original snapshots. Input worlds can contain stale prior-transaction metadata.

## Original empty-account limitation (resolved by final integration below)

Pinned state_tracker.modify_state (569-587) removes an empty account immediately after account mutation; destroy_account also clears storage. World.put merely replaces an account; World.warm_account calls put even for absent accounts. The model has exists and warm flags but no independent account-mutation/touch journal. A final sweep of every empty account is unsound: untouched preexisting empty accounts and read-only warm entries are not mutation evidence. A final sweep of warm empties is likewise unsound. Exact mutation-triggered deletion needs explicit tracked mutations (including zero-fee coinbase credit) or carefully updated state-changing helpers, journaled with frame rollback. This is a real integration/coverage limit if only transaction files are changed. Document it; do not describe blanket final normalization as complete EELS equivalence.

## Second implementation review

Reviewed newly compiled `transaction.bend`, `transaction-finish.bend`, `transaction-world.bend`, `transaction-validate.bend` and intrinsic implementation. The preparation snapshot is after sender debit/nonce and before auth; dispatched rollback snapshot is after auth/dispatch costs and before create initialization/value transfer. Auth counters are saved then zeroed before dispatch. CREATE correctly ignores existing storage in collision, clears both storage and original, and uses empty calldata. One-hop delegation suppresses precompile execution with empty code and leaves destination context intact. Finish rejects nonterminal/HostLimit with Incomplete, avoiding publication of a partial world through that API. Gas floor formula and fee/destruction order are correct by source inspection.

Concrete bug reported to lead: validation uses 49152-byte initcode cap. Pinned transactions.py validate_transaction imports MAX_INIT_CODE_SIZE from interpreter.py; the latter defines 2*65536=131072. Threshold must be 131072. Add validated length boundary coverage at 49153, 131072 and 131073. This review did not execute tests, and does not remove existing touched-empty/nested-helper limitations.

## Final integration review: resolved cleanup and initcode findings

The prior empty-account gap is resolved for the reviewed mutation paths by `World.modify` and the four-module `transaction-world-integration.patch`. `World.put` remains metadata-only; warming uses put. `modify` immediately marks an empty modified leaf absent and clears persistent storage while preserving transaction warmth, original slots and transient metadata in an absent-account tombstone. This supplies the needed distinction without adding a touched field. Existing whole-world frame snapshots journal the resulting mutation. Transfers, sender nonce/upfront writes, authorization writes, create nonce/code writes, fee credits and destruction now route through modify. SELFDESTRUCT uses `World.move_ether` even for zero balance, so its zero-value beneficiary touch is retained; ordinary message zero transfer still does nothing. Thus the earlier statement that the model cannot distinguish mutation from warming is no longer a current transaction-layer limitation. Callers exporting accounts must respect `exists=False` tombstones rather than count every list entry as a state leaf.

The initcode validation threshold is now 131072 in transaction-validate.bend, correcting the reported defect. Source inspection confirms the final cleanup patch and threshold. Existing recorded logs inspected: transaction-finish-tests JS/native each contain 21 PASS cases, including modified-empty storage cleanup, metadata retention, mere warming, journal rollback, zero SELFDESTRUCT, balance draining and coinbase fee preservation; transaction-acceptance-execution JS/native each contain 13 PASS cases. The acceptance-validation-native log inspected contains 17 PASS cases; the lead separately reports a 29-case native validator suite, not independently verified in this audit. No heavy test execution was performed by the auditor.

Remaining pre-existing nested CREATE findings are separate from the resolved empty-account integration: create-enter collision still rejects nonzero storage, and its destination initialization still does not clear original slots. Top-level transaction create implements the correct rules. No claim of complete nested-runtime conformance or external differential coverage follows from this transaction review.
